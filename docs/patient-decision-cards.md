# Карта пациента и карточка решения — первая рабочая версия

Карточки работают поверх существующих контрактов и выдаются прямо в Codex.
Это локальные представления данных, не новый веб-сервис и не диагностическая система.
В этом изменении реальные архивы не читаются, не синхронизируются и не изменяются.

## Две карточки

**Карта пациента** — снимок одного явно выбранного выпущенного `CasePacket`.
Наблюдения сохраняют исходные значения, единицы, референсы, метод, дату и
происхождение. Факт из источника, сообщение пользователя и расчёт — разные
категории. Дата сборки пакета не подменяет дату исследования.

Контекст содержит лекарства, добавки, аллергии, состояния, симптомы и цели.
Оператор может связать раздел с существующими ID записей, но такая связь
означает только наличие записи в выбранном пакете. Она не подтверждает
актуальность, медицинскую правильность или отсутствие противопоказаний.
Неизвестные сведения остаются неизвестными.

**Карточка решения** — один вопрос, явная цель, варианты, польза, риски,
дозировка, длительность, контроль, альтернативы, применимость и неопределённость.
Все медицинские формулировки в вариантах берутся из конкретных утверждений
`AnswerBundle`, а не из дополнительного свободного текста. Их основания,
популяция, ограничения, исходные оценки доказательств и места в источниках
остаются доступны в полном представлении.

Статусы:

- `research_needed`: исследования, проект ответа или основания вариантов ещё не подготовлены.
- `draft`: структурно допустимый черновик, не медицинское одобрение.
- `blocked_clinician_confirmation`: клиническое действие требует подтверждения;
  эта версия карточек его не выдаёт и не принимает заявление оператора за receipt.

Карточка не выбирает «лучшее лечение» автоматически. Пустой список недостающих
сведений не означает полноты контекста; указанная категория всегда остаётся
`not_assessed`, пока нет отдельного механизма содержательной оценки.

## Входы и границы

| Вход | Что допускается |
| --- | --- |
| `get_patient_card` | ID выпущенного CasePacket; необязательные связи категория → ID записи |
| `build_decision_card` | вопрос, явный risk envelope, ID выпущенных пакетов, строгий AnswerBundle, ссылки вариантов на claim ID |
| `cards-demo` | только встроенные вымышленные данные; никаких путей к архивам или JSON пациента |

Оба MCP-инструмента доступны только зоне `synthesis`: stdio, без сети,
без сырого архива, без записи карточек. Пакеты загружаются по ID из
HMAC-проверяемых read-only handoff-хранилищ. Произвольный JSON пакета не принимается.
Публичная, приватная ingest- и audit-роли этих инструментов не получают.
Конфигурация явного списка инструментов сверена с
[OpenAI Docs](https://learn.chatgpt.com/docs/extend/mcp?surface=cli).

Ответ инструмента: `{ "card": <структура>, "markdown": <экранированный текст> }`.
Чистые Python builders проверяют структуру, но сами по себе **не удостоверяют
выдачу** пакета: это делает MCP-хранилище. Не используйте SDK builder как обход
процедуры выдачи и проверки источников.

Неизвестные ID, несовпадающие вопросы/цели/пакеты, отвергнутые утверждения,
подмена типа основания и превышение лимитов приводят к отказу целиком.
Лимиты: 100 записей пациента, 10 вариантов, 100 ссылок вариантов, 100 утверждений
ответа; дополнительно действуют общие ограничения размера и вложенности.
Частичные карточки при превышении лимита не выдаются.

## Как пользоваться

После получения выпущенного CasePacket офлайн-агент вызывает:

```text
get_patient_card(case_packet_id=<issued ID>)
```

Для предварительного плана исследования можно вызвать `build_decision_card`
без `AnswerBundle` и EvidencePacket, но с явным вопросом и целью. Получится
карточка пробелов, а не ответ из памяти модели. После независимой проверки
источников и подготовки `AnswerBundle` варианты связываются с его claim ID;
builder повторно выполняет структурный аудит всех утверждений, включая те,
которые не попали ни в один вариант.

Безопасный пример интерфейса, не использующий реальные данные:

```sh
uv run health-analyzer cards-demo --card patient --format html --output /absolute/new-patient-demo.html
uv run health-analyzer cards-demo --card decision --format html --output /absolute/new-decision-demo.html
```

Файлы создаются только по явно указанному пути и не перезаписываются.
HTML автономный: без JavaScript, внешних ресурсов и активных ссылок.
Markdown и HTML экранируются независимо; источник никогда не исполняется как разметка.

## Что пока не реализовано

- Полная продольная история и разрешение конфликтов между версиями документов:
  существующая лента receipt содержит исторические записи, поэтому молчаливое
  объединение могло бы исказить анализ. Первая версия честно ограничена пакетом.
- Подтверждение актуальности лекарств/аллергий, семантическая проверка назначения
  утверждения полю «польза»/«риск»/«доза» и клиническое ранжирование вариантов.
- Проверка правильности арифметики и полноты зависимостей расчёта. Статус
  verified означает проверку записи, а не новый математический аудит.
- Регулируемая клиническая система, автоматические назначения, подпись врача,
  сетевой экспорт или отправка данных из карточек.

Tests demonstrate implementation behavior and traceability, not clinical
correctness. The checked-in patient and decision-card examples use fictional
data only. Regenerate them locally with the documented commands whenever their
builders or schemas change.
